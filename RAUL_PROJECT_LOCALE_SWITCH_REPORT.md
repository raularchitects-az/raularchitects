# Raul Architects — Project Locale Switch Report

**Date:** 2026-08-23  
**Issue:** Language switcher on Project detail pages could navigate to literal `[slug]` URLs (e.g. `/en/projects/[slug]`), causing 404.  
**Status:** Fixed — no commit, push, or deploy

---

## Root cause

Project detail pages did not register locale-specific hrefs with the shared language switcher.  
`usePathname()` on dynamic routes returns the internal template (`/layihelar/[slug]`), and `router.replace(pathname, { locale })` produced broken localized URLs without the real slug param.

Blog and Insights detail pages already solved this via `BlogLocaleSwitch`; Projects did not.

---

## Changed files

| File | Change |
|------|--------|
| `src/lib/project-urls.ts` | **New** — `buildProjectLocaleSwitchPaths(slug)` resolves per-locale project detail or listing fallback |
| `src/lib/locale-switch-fallbacks.ts` | **New** — client-safe listing fallbacks for unresolved dynamic pathnames |
| `src/app/[locale]/layihelar/[slug]/page.tsx` | Registers `BlogLocaleSwitch` with resolved paths for every locale |
| `src/components/language-switcher.tsx` | Safety net: if no override and pathname is a dynamic template, navigate to that section’s listing page |

---

## Fix behaviour

For **every** project (CMS + legacy, present and future):

1. On project detail render, `buildProjectLocaleSwitchPaths(slug)` checks `getPublicProject(slug, locale)` for AZ, EN, DE, RU.
2. If the project exists in that locale → `{ pathname: "/layihelar/[slug]", params: { slug } }` (next-intl localizes to `/projects/…` in EN).
3. If not available → `/layihelar` (EN: `/projects` listing).
4. Language switcher always prefers these overrides; never emits literal `[slug]`.
5. Same project slug is preserved across locales (projects use one canonical slug, unlike Insights/Blog).

**Unchanged:** URL architecture, localized route names, slugs, CMS data, SEO, design, Insights, admin.
